# Нагрузка на LogFlux универсальным генератором

LogFlux — один из сценариев, его формат не зашит в Go-код генератора.

## 1. Сначала проверить генератор отдельно

Из корня LoadGenerator:

```bash
./bin/load-generator -sink 127.0.0.1:8090
```

В другом терминале:

```bash
export LOGFLUX_API_KEY='test-only'
./bin/load-generator -config scenarios/logflux.yaml -check-config
```

Чтобы сохранить все настройки сценария и сменить адрес, сделайте копию YAML **в папке scenarios** и поменяйте только `targets[0].url` на `http://127.0.0.1:8090/api/v1/logs`. Затем запустите копию через `-config`. Флаг `-url` для этого не подходит: он заменяет цель целиком, включая тело и заголовки.

## 2. Подключить реальный LogFlux

1. Запустите сервисы, Kafka и БД.
2. Создайте проект и ключ с правом записи.
3. Проверьте реальный endpoint и ожидаемую JSON-схему. Пример нацелен на `POST /api/v1/logs` из ТЗ.
4. Задайте ключ и запустите небольшой тест:

```bash
export LOGFLUX_API_KEY='your-write-key'
./bin/load-generator -config scenarios/logflux.yaml -check-config
./bin/load-generator -config scenarios/logflux.yaml -stages '10@10s'
```

Профиль требует ответ **202**. На момент первоначальной интеграции в LogFlux был `/api/logs` с пустым обработчиком и DTO `event_id`; текущую реализацию проверьте перед тестом. Пустой обработчик с ответом 200 будет отмечен как неуспех в этом профиле.

## 3. Что именно отправляется

`scenarios/bodies/logflux-batch.json.tmpl` содержит `{"logs":[...]}` со **100 событиями**. У каждого — новый `eventId`, текущее время, сервис, окружение load-test, уровень и 512 символов сообщения. UUID разных вхождений не повторяются в пределах запуска. Пять записей из ста имеют уровень ERROR.

Шаблон читается один раз, динамические поля меняются в переиспользуемом буфере. Увеличить пакет — добавить записи в массив шаблона; уменьшить — удалить. Изменить длину message — заменить `{{random:512}}`. Этот шаблон намеренно содержит случайный текст: он не моделирует хорошую сжимаемость реальных повторяющихся логов.

Для snake_case API измените ключ на `event_id`, регистр уровня и обёртку тела согласно реальному контракту. Нельзя определить форму тела только по DTO: посмотрите, что декодирует handler.

## 4. Считать нагрузку

При 100 событиях в пакете:

| RPS | Событий/с |
|---:|---:|
| 100 | 10 000 |
| 1 000 | 100 000 |
| 5 000 | 500 000 |

Сам генератор считает HTTP-запросы и байты и не интерпретирует содержимое как логи. Размер пакета напечатает `-check-config`. LogFlux может ограничивать тело 1 MiB и 500 событиями — соблюдайте ограничения целевого API независимо от лимита генератора 16 MiB.

## 5. Оценивать весь конвейер

Отчёт генератора показывает только HTTP. Дополнительно смотрите Kafka lag, ошибки обработки, число уникальных событий в ClickHouse и задержку до поиска. При timeout сервер мог принять запрос; автоматических повторов нет. Ограничитель проекта может возвращать 429 — это отдельный результат, а не обязательно предел Kafka/ClickHouse.

Для нескольких проектов добавьте несколько целей с разными `api_key_env` и весами. Не публикуйте ключи в YAML. Один и тот же файл тела можно подключить к каждой цели.
