# Load Generator

Нативный универсальный HTTP-генератор нагрузки на Go. Несколько endpoint’ов, произвольные методы, заголовки, статические/динамические тела, ступени общего RPS. Не зависит от формата LogFlux, Kafka или какой-либо БД.

## Быстрый запуск

```bash
go build -o bin/load-generator .
# В отдельном терминале — необязательный тестовый приёмник:
./bin/load-generator -sink 127.0.0.1:8090
# Проверка без сетевых запросов:
./bin/load-generator -config scenarios/local.yaml -check-config
# Нагрузка:
./bin/load-generator -config scenarios/local.yaml
```

Приёмник читает до 16 MiB тела, отвечает 202 и ничего не сохраняет. Принимает различные HTTP-методы. Docker не требуется. Go 1.24+.

## Настройка

```yaml
targets:
  - name: catalog
    url: http://localhost:8080/items
    weight: 80
    method: GET
    expected_status: [200]
  - name: create
    url: http://localhost:8080/items
    weight: 20
    method: POST
    headers:
      Content-Type: application/json
    # Значение заголовка целиком берётся из окружения:
    # headers_env:
    #   X-API-Key: MY_API_KEY
    # Для Bearer удобнее:
    # api_key_env: MY_BEARER_TOKEN
    body_template: '{"id":"{{uuid}}","value":"{{random:256}}"}'
    expected_status: [201, 202]
load:
  stages:
    - rps: 100
      duration: 10s
    - rps: 1000
      duration: 30s
limits:
  concurrency: 256
  payload_memory_mib: 128
  request_timeout: 5s
report:
  path: ./report.json
```

RPS — общий для всех целей. Веса задают приблизительные доли; сумма не обязана равняться 100. Один запрос направляется одной цели. При перегрузке реальные доли могут отличаться. Метод по умолчанию GET, тело пустое, успех — любой 2xx, если `expected_status` не задан. Content-Type автоматически не добавляется.

Имена целей уникальны; weight обязателен и положителен. Неизвестные YAML-поля, неправильные значения и отсутствующие секреты вызывают ошибку до начала теста. Переменные `${ENV}` не подставляются автоматически.

## Тело запроса — один вариант на цель

| Поле | Поведение |
|---|---|
| `body` | Статическая строка, можно использовать YAML `|` |
| `body_file` | Файл произвольного содержимого, включая бинарное; читается один раз |
| `body_template` | Строка с подстановками |
| `body_template_file` | Файл с подстановками, компилируется один раз |

Пути файлов тела в YAML считаются **от папки YAML**. Путь отчёта считается **от рабочей папки запуска**. Лимит тела — 16 MiB. Статические файлы передаются без интерпретации `{{...}}`. Содержимое не проверяется как JSON — можно отправлять XML, текст и другие форматы.

Шаблон поддерживает только фиксированные подстановки:

| Подстановка | Значение |
|---|---|
| `{{uuid}}` | Уникальный UUID для каждого вхождения/запроса в пределах запуска |
| `{{timestamp}}` | Текущее время UTC, RFC3339 с наносекундами |
| `{{sequence}}` | Номер запроса, 20 цифр с ведущими нулями |
| `{{random:512}}` | 512 случайных ASCII-символов, безопасных внутри JSON-строки |

В JSON все подстановки помещайте **в кавычки**, включая sequence. Они предназначены для тела, не URL или заголовков. UUID содержит случайный префикс запуска и счётчик; это не криптографический случайный UUID. Неизвестные placeholders отклоняются. Статические данные с {{...}} используйте в `body`/`body_file`.

## Флаги и приоритет

Defaults → YAML → явно переданные флаги.

```bash
./bin/load-generator -config scenarios/local.yaml -concurrency 512 -stages '200@10s'
./bin/load-generator -url http://localhost:8080/health -method GET -stages '100@10s'
./bin/load-generator -url http://localhost:8080/upload -method PUT -body-file ./sample.bin
```

- `-url` заменяет весь список целей одной новой целью (сбрасывает YAML-заголовки, тело и ожидаемые статусы).
- `-method` переопределяет метод всех выбранных целей.
- `-body-file` заменяет тела всех выбранных целей; путь от рабочей папки.
- `-key-env` задаёт Bearer-переменную для всех целей. Секреты не печатаются в отчёте; храните их в окружении.
- `-stages`, `-concurrency`, `-memory-mib`, `-timeout`, `-report` переопределяют соответствующие настройки.
- `-check-config` показывает план и завершается без запросов и отчёта.

Старые `-batch`, `-message-bytes`, `-services`, `-format` и YAML-секция `payload` **удалены**: формат данных теперь полностью задаётся телом запроса. Для LogFlux используйте отдельный шаблон из [инструкции](docs/logflux.md).

## Производительность и ограничения

Тела шаблонов подготовлены заранее. Каждый worker переиспользует отдельные буферы для целей, а фиксированные поля обновляются без сборки JSON. Память ограничена суммарным размером тел всех целей: общий набор плюс по набору на worker. Бюджет автоматически снижает concurrency; это **не лимит RSS**. Пустые GET-запросы не выделяют payload-буфер.

HTTP/1.1 keep-alive, общий транспорт, ограниченная параллельность. Заголовки и Content-Length формируются транспортом; Host/Connection/Transfer-Encoding нельзя переопределять. Redirects и прикладные retries отключены. TLS проверяет сертификаты. Системные HTTP_PROXY/HTTPS_PROXY/NO_PROXY учитываются.

Планировщик работает с шагом около 1 мс, отправки имеют микровсплески. При нехватке слотов растёт Missed, бесконечной очереди нет. Медленная цель может занять общие слоты и повлиять на остальные — для полной изоляции запускайте отдельные процессы.

Нет сценариев с зависимостями запросов, извлечения токенов из ответов, WebSocket/gRPC, сжатия, автоматической сверки с БД и распределённого координатора. 100 000 RPS не является гарантией. Производительность измеряйте на своём оборудовании с нужным размером тела.

## Отчёт

Сводка раз в секунду и JSON после теста. Ctrl+C сохраняет частичный отчёт. Существующий отчёт перезаписывается.

- Scheduled = Submitted + Missed.
- Started/Completed — вызовы HTTP и завершения; Success — ожидаемые статусы с успешно прочитанным телом ответа.
- targets — Started/Success/Errors по именам целей; ключи и URL не сохраняются.
- TransportErrors/ResponseErrors — сетевые ошибки и ошибки чтения тела.
- LatencyP50/P95/P99 — от начала HTTP до чтения ответа; пропуски не входят в latency.
- StartLagP99 — отставание от планового времени отправки.
- Процентили по фиксированной гистограмме — приблизительные верхние оценки (~6.25% разрешение).
- PayloadBytes — **максимальный размер тела цели**, а не средний.
- SubmittedPayloadBytes — сумма размеров тел попыток, не фактический сетевой трафик.
- HeapBytes — Go heap в конце, не RSS и не пиковое значение.
- Stages.Duration — наносекунды. AchievedStartRPS — среднее за весь профиль, включая медленные ступени.

HTTP-успех не доказывает сохранение данных приложением. При сравнении запусков фиксируйте оборудование, размер тела, метод, TLS, concurrency и профиль RPS. План не выводит query string, тела или заголовки; не помещайте секреты в имена целей или URL-пути.
