# Load Generator

Нативный HTTP-генератор на Go без внешних зависимостей. Ступенчатая открытая модель нагрузки: скорость задаётся независимо от ответов, при нехватке ресурсов отправки учитываются как `Missed`, а не копятся бесконечно.

## Сборка

```bash
go build -o bin/logflux-load .
```

Go 1.24+. Запускать команды из этой папки. Docker не требуется.

## Быстрая проверка

Терминал 1 — синтетический приёмник, который читает тело и отвечает 202:

```bash
./bin/logflux-load -sink 127.0.0.1:8090
```

Терминал 2:

```bash
./bin/logflux-load -url http://127.0.0.1:8090/api/v1/logs \
  -stages '100@10s,1000@20s,5000@20s' \
  -batch 100 -message-bytes 512 -concurrency 256 \
  -memory-mib 128 -report report.json
```

Sink НЕ валидирует JSON и НЕ сохраняет события. Он нужен для проверки транспорта генератора. Запуск на одном компьютере измеряет общие ограничения генератора и приёмника.

## Настройки

| Флаг | По умолчанию | Значение |
|---|---|---|
| `-stages` | `100@10s` | RPS@длительность, через запятую |
| `-batch` | 100 | Событий в запросе, 1–500 |
| `-message-bytes` | 512 | Размер поля message; событие больше за счёт остальных полей |
| `-services` | 20 | Количество синтетических имён сервисов |
| `-concurrency` | 128 | Максимум принятых планировщиком запросов в работе |
| `-memory-mib` | 128 | Бюджет переиспользуемых payload-буферов, НЕ лимит RSS |
| `-timeout` | 5s | Таймаут HTTP-запроса |
| `-format` | logflux | logflux либо legacy |
| `-report` | report.json | Итоговый JSON, существующий файл перезаписывается |

Бюджет памяти автоматически уменьшает число workers. Отдельно расходуются память HTTP/TLS, стеки, метрики и служебные структуры. При нехватке памяти не поднимайте concurrency вслепую. Тело запроса ограничено 1 MiB. Все запросы имеют одинаковый batch; сообщения различаются. Примерно 5% событий — ERROR (для маленьких batch доля округляется).

RPS — запросы в секунду. События/с = RPS × batch. При batch=100 и размере события около 1 KB, 1000 RPS — около 100 MB/с полезных тел. Report.PayloadBytes показывает размер одного примерного пакета.

## Как устроено

- Ограниченный пул workers, свой переиспользуемый буфер у каждого.
- Payload собирается один раз; UUID, время и ASCII-содержимое меняются без повторного JSON marshal. UUID содержит случайный префикс запуска и 62-битный счётчик событий.
- Синтетические сообщения имеют высокую энтропию: это нагрузочный профиль для сжатия, а не модель реальных бизнес-логов. Replay файла и другие распределения пока не реализованы.
- Общий HTTP/1.1 transport, keep-alive, ограниченный пул соединений; прикладных retries нет. Большие/неисправные ответы не читаются без ограничения.
- Планировщик работает с шагом около 1 мс, поэтому отправка имеет микровсплески. Это не Poisson arrival и не точный таймер на каждый запрос.
- При отставании не воспроизводится бесконечный backlog: пропущенные слоты учитываются. Измеряется задержка между плановым временем и началом HTTP-запроса.
- На завершении этапов ожидаются ответы с настроенным timeout; Ctrl+C отменяет запросы и сохраняет частичный отчёт.

## Отчёт

Сводка раз в секунду и JSON после завершения:

- Scheduled = Submitted + Missed; пропуски не включаются в latency.
- Started/Completed — вызовы HTTP и завершения; Success — ответы 2xx с успешно прочитанным ограниченным телом.
- Statuses, TransportErrors, ResponseErrors — HTTP-коды, сетевые ошибки и ошибки чтения ответов.
- LatencyP50/P95/P99 — время от начала HTTP до прочтения ответа, включая ожидание соединения; StartLagP99 — отставание от расписания.
- Процентили — верхние оценки по фиксированной логарифмической гистограмме (~6.25% разрешение), ограниченные наблюдавшимся максимумом.
- AchievedStartRPS — число стартов / время подачи нагрузки; TotalSeconds также включает завершение запросов.
- SubmittedPayloadBytes — байты тел попыток, не измеренный сетевой трафик. Неуспешная попытка могла передать только часть тела.
- HeapBytes — Go heap в конце, не RSS и не максимум за весь тест.
- Stages.Duration в JSON — наносекунды.

Отчёт не содержит API-ключа или целевого URL. RunID позволяет связать запуск с UUID событий. Автоматическая сверка с ClickHouse, Prometheus-экспорт, YAML-сценарии, сжатие и координация нескольких машин пока не реализованы. Отдельные процессы можно запускать вручную с собственной долей нагрузки и разными путями отчётов; их p99 нельзя усреднять.

**2xx не доказывает сохранение событий.** Для end-to-end измерений отдельно проверяйте Kafka lag, число уникальных событий и задержку до ClickHouse. Для сравнимых результатов фиксируйте CPU, RAM, сеть, payload, concurrency, версии сервисов; перед основным замером прогревайте соединения. 100 000 RPS не является обещанием производительности.

## Проверки

```bash
go test -race ./...
go test -run '^$' -bench BenchmarkPayload -benchmem
go vet ./...
```

Проверяются JSON/UUID, уникальность событий, счётчики, перегрузка, отмена, redirects и ограничения. BenchmarkPayload измеряет только обновление JSON-буфера, не HTTP или всю платформу.
